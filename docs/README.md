## 阅读顺序

1. 接手项目：根 README -> 本索引 -> [当前状态与问题台账.md](当前状态与问题台账.md) -> 当前 [设计评审稿](场景化审核Agent需求与设计评审稿.md) -> 与任务相关的历史契约和当前代码。
2. 修改规则库或审核链路：先核对当前 [设计评审稿](场景化审核Agent需求与设计评审稿.md) 和 [当前状态与问题台账.md](当前状态与问题台账.md) 的冲突说明，再读 [系统设计基线.md](系统设计基线.md) 和 [规则库与审核执行契约.md](规则库与审核执行契约.md) 中仍适用的历史契约。
3. 修改页面：先读 [前端产品与交互规范.md](前端产品与交互规范.md)，再核对真实 API 和当前组件。
4. 排查历史原因时才读取台账第 7 节的历史评审结论；不得按其中旧行号机械修改当前源码。

发生冲突时，不静默挑选对自己方便的说法：用户最新确认的业务决定控制业务口径；真实运行证据控制“是否可用”的结论；当前代码控制“现在如何实现”的判断；稳定文档控制已批准的目标契约。四者不一致时应明确记录到 [当前状态与问题台账.md](当前状态与问题台账.md)。本轮待评审变更尚不是已批准基线，也不得直接按与当前需求冲突的旧条款开工。

## 维护规则

- 不在 `docs/` 新增会话交接、Claude 提示词、阶段计划、交付自述或重复 README。
- 新增目录名、文件名或分类名称前，先按 [GLOSSARY.md](GLOSSARY.md) 检索同义词；同一概念只能有一个名称。
- 易变的实现状态只更新 `当前状态与问题台账.md` 和根 README 的“已知限制”；稳定文档不记录完成百分比或临时代码行号。
- 外部服务字段、枚举和限制没有真实契约或响应证据时，直接写“未知”，不得猜测。
- 文档使用仓库相对链接，不保存个人附件路径、缓存路径或本机业务材料绝对路径。
- “静态已实现”“配置已填写”“真实运行已验证”是三个不同结论，必须分别表述。
- 验收只使用用户提供的真实规则库和真实业务材料；不得用空白文件、生成文件或其他材料槽位的文件替代。
