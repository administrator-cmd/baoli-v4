# 资料、报告与系统管理设计草案

状态：供讨论的设计，尚未实施。现状依据 2026-10-23 当前工作区源码静态核对；本文不作为功能验收记录。

## 职责与导航

任务页承接一笔业务的材料上传、审核执行及结果查看。三个全局模块各自解决跨任务查询、成果查阅和运行排障的问题。

| 模块 | 用户要完成的事 | 建议导航 |
| --- | --- | --- |
| 资料管理 | 找文件、查版本、定位处理异常、追溯使用任务 | 审核材料 |
| 报告管理 | 找报告、读结论、下载成果、汇总风险 | 审核报告、风险汇总 |
| 系统管理 | 判断服务能否使用、定位失败、追溯变更 | 运行状态、操作日志 |

规则库原始 Excel 与导入记录归入场景管理的规则库导入。资料管理集中展示任务材料。任务内保留材料与报告页签，全局页面负责跨任务检索与汇总。

目标使用者：资料和报告面向业务人员；系统管理主要面向维护人员。现有管理员/业务用户是产品职责划分，正式按角色控制入口时，需要实际的身份与后端权限机制，不能只隐藏菜单。

## 资料管理：材料台账

### 当前基础

已有跨任务材料位列表、上传与替换、历史版本。材料绑定任务和材料位；规则库文件页面复用导入作业数据。

### 页面设计

每行表示一个任务的一个材料位，展示当前上传版本；缺件也能被查到。历史文件版本在详情中展开。

- 筛选：任务名称、文件名、材料名称、上传日期、上传情况、处理情况。
- 快捷条件：全部、必传未上传、处理中、处理失败。
- 主表：任务、材料名称、当前文件、版本、处理情况、上传时间、操作。
- 操作：查看原件、下载原件、历史版本、进入任务。
- 详情：原件预览、各版本上传时间与当前标记、材料校验/OCR/解析/印章处理结果及具体错误。

上传、替换、移除在任务中完成，用户能同时看到所影响的审核结果。全局页通过“进入任务”定位到该材料。

处理情况需要读取真实处理产物的状态：材料文件已上传与处理成功分别表达。文件预览、下载和异常筛选需要补齐对应接口与查询；不能仅凭已有列表的单一 status 字段推断四个步骤都成功。

第一版沿用任务材料所有权。跨任务复用文件需要另外确定文件版本、任务引用及删除关系，不能直接让多个任务共享一个会被替换或删除的文件路径。

## 报告管理：成果查阅与跨任务风险汇总

### 当前基础与问题

已有报告查阅、文本下载、备注、归档标记，以及跨任务风险列表。

静态核对发现：

1. `services/report/lifecycle.py` 的归档只修改 archived_at 与 status；任务永久删除仍删除 AuditReport，因此现有归档不代表独立留存。
2. `services/report/query.py` 的当前报告映射按任务取最大报告 id。同一批次可生成多种报告，不能据此把其他报告种类当成历史版本。
3. 下载接口当前输出 Markdown、纯文本或 HTML；PDF、Word 成品导出需要单独实现。

### 审核报告页

每行是一份具体报告，明确报告名称、来源任务和所属执行批次。

- 筛选：报告名称、任务名称、场景、方案、生成时间、当前/历史版本、是否有缺项。
- 主表：报告名称、任务、版本、生成情况、待关注情况、生成时间、操作。
- 操作：阅读、下载、备注、查看任务。
- 阅读页：正文为主，缺项及无法判定原因紧邻正文；来源材料版本、执行批次与配置版本放在详情。
- 同一种报告的版本按“任务 + 报告定义”组织；不同种类报告分别有自己的当前版本。

报告生成、执行范围完整、风险是否能够判定是三个独立事实。“已生成”不能展示为审核通过；部分缺项报告也可以查阅，并直接显示缺项原因。

### 风险汇总页

价值在于跨任务找出需要关注的结果，而任务风险页负责查看单笔任务的完整上下文。

- 快捷条件：已确认风险、无法判断、全部。
- 筛选：任务、场景、方案、风险名称、风险等级、时间。
- 主表：任务、风险编号、风险名称、等级、判断结论、判断摘要、时间、操作。
- 详情保留判断依据、原文及来源材料，并能进入对应任务。
- 汇总同时展示风险条数和涉及任务数；一笔任务命中多条风险，任务只计一次。

风险等级沿用各场景的真实定义；不同场景没有统一等级规则时，按场景分别统计。风险判断结果与后续业务处置状态属于不同数据，不能把“异常”直接解释成“未处理”。

### 归档的两种含义

需要明确选择一种语义：

| 语义 | 用户能得到什么 | 数据要求 |
| --- | --- | --- |
| 收藏/归类 | 标记常用报告，方便检索 | 沿用当前归档标记，页面改名为“收藏”更准确；随任务删除 |
| 正式归档 | 任务清理后，仍可查到报告和可追溯的依据 | 形成独立留存的归档记录，冻结正文、来源版本与必要依据，重新设计删除关系 |

建议第一版把现有标记称为“收藏”。如业务需要正式档案，再按独立留存设计；是否保留原件全文及保留期限应先确定。新增表结构须按仓库约定由用户确认后修改 schema.sql，数据库重建由用户执行。

## 系统管理：运行排障与变更追溯

### 当前基础

服务页会实际探测数据库，外部 LLM/OCR 等只检查配置，返回“已配置，未验证”。操作日志汇集业务操作和后台命令。当前数据不足以给出外部服务实时健康结论。

### 运行状态页

以“哪个环节有问题、影响哪些任务”为主要用途。

- 服务表：服务名称、配置情况、最近一次实际业务调用结果、调用时间、耗时、错误摘要。
- 运行任务：正在处理的任务、真实处理阶段、开始时间、已运行时长、进入任务。
- 失败操作：失败时间、任务/导入作业、失败环节、具体原因、查看详情。
- 已配置、最近调用成功、当前请求失败分别表达；没有调用记录时显示“暂无调用记录”。历史成功不表示当前一定可用。

运行页只读取记录。业务重试回到对应任务或导入页，由原有流程处理结果未知、重复提交与输入版本问题。

需要补齐按服务记录真实调用结果和耗时、失败关联业务对象、查询运行中的操作及其阶段。现有的配置检查不能直接升级文案为“服务正常”。

### 操作日志页

用途是回答“什么对象在什么时候发生了什么变化”。

- 主表：时间、业务对象名称、操作、结果、变化摘要、详情。
- 筛选：对象名称、操作类型、成功/失败、时间。
- 详情：修改前后差异、相关任务或场景入口、错误信息；请求编号与内部编码收在技术详情。
- 记录操作者需接入真实身份；当前无法确定的操作者不能显示为某个用户。

## 实施顺序与边界

1. 调整职责和入口：规则库原件回归场景导入；资料页围绕材料查询，报告页围绕阅读，系统页围绕排障。
2. 修正现有数据含义：报告按种类判断当前版本；明确归档/收藏语义；材料上传与处理情况分开展示。
3. 补齐实用能力：材料预览下载、异常筛选、报告版本分组、风险跨任务汇总、运行中与失败操作查询。
4. 独立档案、跨任务材料复用及角色权限按明确需求另做数据设计。

完成标准：资料页能直接找到文件或处理失败原因；报告页能读到所选种类的当前报告并识别缺项；系统页能从失败定位到具体业务对象。列表和统计依据完整查询范围，不能用当前分页数据冒充全量统计。
