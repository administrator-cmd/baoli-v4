## 0.2 本轮变更：方案改为保存即生效（2026-09-18）

用户判断：与场景那次同源。「草稿 / 发布 / 第 N 版」在方案上同样是多余的认知成本，
且页面上并排的「保存规则选择」与「发布方案版本」两个按钮让主次不分——发布本身
就会先保存，保存只是可省略的中间动作。

变更：方案只有一份配置，保存即生效；`plan_version` 表删除，「版本」概念从页面上消失。
冻结边界从三层收敛为两层，与场景那次一致：场景配置保存即生效 → **方案保存即生效**
→ 任务创建冻结。

| 事项 | 事实 | 状态 |
| --- | --- | --- |
| 保存即生效 | `save_plan` 写规则选择并立即用 `build_task_schema` 重算范围，写进 `audit_plan.scope_json` 与 `scope_hash` | 已在真实库与 HTTP 链路验证 |
| 范围不完整 | 没选规则时保存照常成功但不推进范围，`audit_plan.sync_error` 记录真实原因，页面显示「待核对」，该方案不能被任务引用 | 已确认 |

已执行的真实验证：真实 Excel 上传 → 解析（71 条规则）→ 发布预检查 `ready=true`
→ 发布场景 → 建方案（未选规则时不生效）→ 保存 5 条规则（范围生效）→ 建任务
→ 幂等重发返回原任务 → 改方案为 2 条 → 已建任务仍执行 37 条、新任务执行 31 条。
验证数据已清理，库现为空。

**本轮修掉的一个真实缺陷**：`sync_error` / `scope_json` 是 JSON 列，Python 的 `None`
存成 **JSON 字面量 null**，MySQL 里 `IS NULL` 对它返回假（只有 SQL NULL 才为真）。
按 `sync_error IS NULL` 过滤会让「范围已生效」的方案一条都查不出来——方案下拉为空、
按范围状态筛选失效，而页面看起来一切正常。改用 `JSON_TYPE(...) = 'NULL'` 判断；
场景侧从未按该列做 SQL 过滤，所以没有这个问题。

前端页面未运行验证；规则库导入、审核执行与外部服务未在本轮重跑。

### 1.5.5 本轮发现并修复的一个既有缺陷：金额加总比较被文字判定误拦

核对验收场景时发现：`DECIMAL_SUM_COMPARE`（金额加总比较）**自身就是**合法的字段间加总，
而这条规则在页面表单路径下的能力判定会读到它自己的审核要求原文——
「合同总额等于已付款加未付款」这类句子里必然出现 `SUM_ALL_FILES` 的关键词
（总额/合计/汇总/求和/总计/累计/加总）。结果是**一条系统完全支持、且已正确编译出
三个输入的规则根本存不下来**，报「包含当前不支持的能力：对多份材料做汇总取数」。

导入路径此前不受影响（节点版只对 `parameters.instruction` 做判定，加总比较没有该参数），
所以这条缺陷只在页面手工配置路径上暴露。

修复：新增 `manifest.detect_unsupported_capability_for_operator(operator, *texts)`，
对**输入形态为 `FIELD_LIST` 的算式算子**跳过 `SUM_ALL_FILES` 与 `CROSS_PERIOD_TOTAL`
两个码——它们的关键词逐一核对过，与「总额等于已付款加未付款」「各项金额分期汇总后与总额一致」
这类正常写法重叠。跳过的是**文字判定**，不是能力判定：

- 这两个码真正要拦的越界（无界聚合、跨期自动累计）在算式算子上由**结构约束**拦下：
  必须显式列出参与相加的字段（编译期校验至少两个），系统不会自行跨文件取数；
- 用户真要求跨文件无界聚合时，措辞落在仍生效的 `MULTI_FILE_AGGREGATE`（「所有发票合计」）
  与 `MULTI_CONTRACT_GROUP`（「全部合同」）上，实测仍被拦下；
- `CONSTANT_COMPARISON`、`EXTERNAL_LOOKUP` 与加总措辞无关，在算式算子上照常生效。

非算式算子走完整判定，行为不变。三个使用点（页面编译、导入编译、导入期汇总）统一改调新函数。

### 1.5.6 本轮明确不做

- **不改** 主体检索的单一产物来源（`SUBJECT_ARTIFACT_SOURCE = "SEAL"`）：触发条件已由字段的「产物来源」列声明解耦，抽象第二个检索源目前没有真实依据；
- **不扩展** 日期/金额标准化的中文写法表与币种表：扩展它们需要业务先确认口径，否则是代填默认值；
- **不改** 固定十节报告的章节结构：改成配置驱动需要业务先给出报告结构口径；
- **不实现** PDF/Word/Excel 文件生成，也不为它们造空文件；
- **不新增** 默认 handler、默认阈值、默认单位或静默跳过路径。

### 1.5.6 本轮发现并修复的第二个既有缺陷：候选修正弹窗会清空未呈现的参数

`CandidateCorrectionDialog`（导入工作台的「修改候选内容」）的 `buildParameters()`
原先从**空对象**开始拼 parameters，只写它自己列出的几个算子分支。
`DECIMAL_SUM_COMPARE`、`FIELD_NOT_EMPTY`、`CLAUSE_ABSENT`、`DECIMAL_CN_EQUAL`
都不在分支里，于是编辑这些规则时提交的是 `{}`——一次「只改个名字」的操作就会把
这条规则的比较方向与允许差值整体抹掉，而且弹窗上完全看不出发生了什么。

修复三处：

| 事项 | 变更 |
| --- | --- |
| 参数基线 | `buildParameters()` 改为以候选**现有 parameters** 为基础，只覆盖弹窗真正呈现的键；未呈现的键原样保留 |
| 加总比较参数 | 补 `DECIMAL_SUM_COMPARE` 的方向与允许差值表单（此前它连输入项都没有，提交必然丢参数） |
| 假算子 | `ruleOperatorOptions` 移除非规则算子 `MATERIAL_EXISTS`——它挂在材料检查节点上，不来自规则工作表；保留它会让这个下拉里出现一个后端从不接受的选择 |

这是上一轮审计（§ 六、五）列在「运维级硬编码」里的同类问题：**同一份算子名单在多处维护**。
本轮的能力目录消除了页面下拉那一份，这个弹窗是另一份。

### 1.6.2 三个列表页的 MySQL 排序缓冲溢出（1038）

真实报错（已复现）：`(pymysql.err.OperationalError) (1038, 'Out of sort memory, consider increasing server sort buffer size')`。

根因：查询用 `select(NodeExecution, AuditTask, ScenarioNode, ScenarioVersion)` 取**整行实体**，
再 `ORDER BY created_at DESC`。MySQL filesort 把整行（含 `scenario_version.manifest_json` =
**223,989 字节**）塞进排序缓冲，而本机 `sort_buffer_size` 只有 **262,144 字节**。
实测确认：**只要有 1 行就会 1038**，与表里有多少数据无关（当时 `node_execution` 仅 12 行）。

修复方式与同文件 `list_import_jobs_page` 的既有写法一致——**只 SELECT 列表真正用到的列**：

| 函数 | 修复前 | 修复后 |
| --- | --- | --- |
| `list_executions_page` | ✗ 1038 | ✅ total=12 |
| `list_risk_results_page` | ✗ 1038 | ✅ total=11 |
| `list_reviews_page` | 侥幸未爆（数据仅 1 行） | ✅ total=1 |
| `list_reports_page` | 侥幸未爆（数据仅 0 行） | ✅ total=0 |

后两个函数 join 了同一个带大列的表，属于**同一缺陷**，只是当时数据量小没触发；
本轮一并修复，避免数据增长后再爆。返回字段与前端 `ExecutionRow` 等契约逐字段比对一致。

### 7.1 合并结论

| 编号 | 当时发现 | 最终设计决定 |
| --- | --- | --- |
| I01-I03 | 导入只覆盖预览范围、映射与引用重建不完整、合法参数不等于忠实原文 | 完整读取并逐来源处置；profile 确定性解析；参数、来源和人工确认可追溯 |
| I04-I05 | 候选纠错和发布意图恢复不完整，预检查可能沿用旧目标或旧输入 | 使用可修订草稿；预检查绑定目标、修订和哈希；改变输入后重新检查 |
| I06-I07 | 导出可能丢有效参数；报告章节要求与最小场景冲突 | 导出必须语义等价并按原 profile；系统报告能力与可选业务章节分开 |
| A01-A03 | 人工复核状态入口矛盾；字段和规则复核顺序错误；错值/漏值缺主动纠错 | 先复核事实再重算规则；事实和规则都要有可操作纠错入口 |
| A04-A05 | 重抽取覆盖事实、旧复核可能套用新值；首次补传不一定触发重算 | 不可变事实与当前选择分离；所有输入变化产生修订并失效依赖 |
| R01-R03 | 对象锁、幂等输入和图/业务提交之间存在恢复窗口 | 先锁后检查；幂等键核对完整输入；持久命令、业务结果和 checkpoint 对账 |
| E01-E03 | 文件质量契约、OCR 未知状态和证据定位不完整 | 只按真实服务能力执行；结果未知不自动重发；没有可靠映射不伪造页码或坐标 |
| E04-E05 | 规范值、Decimal 比较、单位口径和能力判定可能不一致 | 服务端按明确类型规范化；确定性工具校验单位、类型和适用性，缺证据不通过 |
| U01 | 切换任务、轮询、风险计数和读取失败的界面状态可能串联或误导 | 响应绑定对象和请求代次；异常、未知、空数据和历史结果分别显示 |
| O01-O02 | 报告展示与结构化信号不一致，错误定位信息不足 | 报告使用统一事实快照和三类信号；返回安全的业务定位和稳定错误码 |
| D01 | 初始化脚本不能证明旧库结构正确，数据库与文件备份边界不清 | 空库初始化与保留数据升级分开；升级前同一时间点备份数据库和文件 |

这些决定已经分别整理进当前 [系统设计基线.md](系统设计基线.md)、[规则库与审核执行契约.md](规则库与审核执行契约.md)、[前端产品与交互规范.md](前端产品与交互规范.md) 以及仓库根 README 的数据库运行说明。当前是否实现只看本台账和最新代码。

### 7.2 已裁定的不采纳意见

- “产物表没有唯一约束”和“发布没有 commit”是当时误报，不据此添加重复结构。
- MySQL saver 使用 `autocommit` 不能推出依赖包内部事务不原子；应用只处理业务事务与 checkpoint 之间的对账。
- 报告三信号的 DTO 当时已经存在，正确方向是统一口径，不是另建平行 DTO。
- 不能仅凭静态路径断言必传材料一定可绕过、历史结果一定重复或供应商 URL 已构成可利用 SSRF。
- 不在 Excel 中增加 JSON、内部技术 ID 或强制所有旧格式升级来换取实现方便。
- 不取消事实报告，不要求所有高风险规则逐条点击，也不要求每个人工值都有机器坐标引文。
- 没有真实供应商幂等或查询契约时，不能承诺外部请求绝不重复。
- 逐来源处置不等于“一行必须生成一条规则”；有依据的合并和拆分必须保存关系。
