## 2026-10-27 通过 http://IP 访问时请求全部失败

现象：用局域网/公网 IP 以 http 打开页面，场景列表显示「读取失败：crypto.randomUUID is not a function」。

改为 `src/utils/ids.ts` 的 `newId()`：用所有上下文都有的 `crypto.getRandomValues` 生成 32 位十六进制，与后端 `uuid4().hex` 同形。替换三处：

- `src/api/http.ts` 请求头 `X-Request-ID`、上传请求的 `X-Request-ID`
- `src/views/plans/PlanEditView.vue` 新增章节时的 `section_key`

核对：`npm run typecheck` 通过；从隧道取 `src/api/http.ts`、`src/utils/ids.ts`、`PlanEditView.vue` 的编译结果，`randomUUID` 已无引用，`newId` 正常导出。

## 2026-10-28 风险结果列表加载慢的原因

现象：`/api/risk-results` 单次 1.8–2.4s，同样体量的 `/api/reports`、`/api/documents` 都是 8–11ms。

分段计时（`list_risk_results_page` 单次调用共 2.50s）：

| 查询 | 耗时 |
| --- | --- |
| `risk_levels`（去重等级） | 827 ms |
| `total`（总数） | 678 ms |
| `rows`（当页 20 行） | 769 ms |
| `hit_count` | 41 ms |
| 锁文件、读 RuleResult、读取值 CSV 等 | 各 5–13 ms |

慢在三个共用同一谓词的查询上，其余都很快。根因是 `risk_rule` 条件（`services/report/risks.py:36`）：

```sql
json_contains(audit_task.manifest_json, json_object('rule_key', rule_result.rule_key, 'rule_role', 'RISK'), '$.rules')
OR json_contains(audit_task.manifest_json, json_object('rule_key', rule_result.rule_key, 'operator', 'RISK_TRIGGER'), '$.rules')
```

`manifest_json` 平均 705,881 字节（约 690 KB），这个谓词要按 join 出的每一行求值，236 条规则结果就是约 160 MB 的 JSON 解析，且两个 OR 分支各解析一次，任何索引都用不上。执行计划里 `rule_result` 走 `uq_rule_result_execution_rule` 索引后仍需逐行 `Using where` 求值 JSON。

隔离验证（同一个 count 查询）：

| 条件 | 结果 | 耗时 |
| --- | --- | --- |
| 无 JSON 谓词 | 236 | 15 ms |
| 只加「当前批次」 | 236 | 6 ms |
| 只加「待重跑排除」 | 236 | 4 ms |
| 只加风险身份（JSON） | 23 | 554 ms |
| 三者全加 | 23 | 680 ms |

即 550ms 以上全部来自 `manifest_json` 的 JSON_CONTAINS。`hit_count` 只要 41ms，是因为叠加 `status = 'ABNORMAL'` 后取数行数变少。

补充事实：`rule_result` 上没有规则角色列；同样的判断在任务详情里是用 `domain/rule_library.py:is_risk_rule` 在 Python 侧对 manifest 做的（`services/audit/views.py:38`、`:185`）。

可选的两种改法（尚未实施）：

1. 执行时把规则角色落到 `rule_result` 上（新增一列 + 迁移 + 回填），列表按列过滤，JSON 不进入查询；
2. 请求内先取当前范围内任务的 manifest（本次只有 3 个任务），用 `is_risk_rule` 算出各任务的 `rule_key` 集合，再换成 `IN` 条件，无需改表，但任务数量大时会线性变慢。

本轮只做定位，未改动任何代码、未运行测试与构建。临时计时脚本已删除。
