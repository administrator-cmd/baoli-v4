# 后端分层约定

代码按实际职责分层，不建空接口、repository 层或额外包装。

## 目录

| 目录 | 职责 |
| --- | --- |
| `app/main.py` | 创建应用、注册路由、启动检查 |
| `app/api/routes.py` | 汇总各模块 router |
| `app/modules/<业务>/<实体>/` | 该实体的路由、模型、数据访问和服务 |
| `app/core/` | 配置、数据库会话、CRUD 基类、ORM 基类、响应基类 |
| `app/domain/` | 配置结构、引用编译、值转换、工具目录；不访问数据库 |
| `app/graphs/` | LangGraph 任务图和单条规则执行器 |
| `app/integrations/` | LLM、文档解析、OCR、印章等外部服务 |
| `app/operators/` | 本地工具算子 |
| `app/services/shared/` | 跨业务共用能力 |
| `app/middleware/`、`app/common/`、`app/runtime/` | 请求上下文、异常、启动检查 |

实体目录固定为：

```text
modules/<业务>/<实体>/
  controller.py   HTTP 路由
  dto.py          请求参数
  schema.py       响应模型（VO）
  model.py        数据库实体或 JSON 配置数据类
  crud.py         数据库读写
  service/        业务编排
```

请求用 `dto.py` 的 `XxxRequest`，响应用 `schema.py` 的 `XxxResponse`；分页和列表筛选参数在 `app/schema/query/`，通用响应结构在 `app/core/base_schema.py`。

分页响应使用 `PagedResponse[具体行模型]`，列表行在所属实体的 `schema.py` 声明；风险命中数、操作日志等业务响应也留在所属模块，不放进通用基类。任务详情的方案身份、材料、字段、规则结果与统计使用明确模型；冻结节点和字段配置的扩展属性沿原结构保留，业务取值及执行结果中的动态内容不靠字段名猜测类型。

## 依赖方向

controller → service → crud → model。

- controller 只处理 HTTP：入参、依赖注入、响应组装。
- controller 不相互导入响应包装函数；复用响应模型和 `ok`。跨模块调用使用明确的公共服务方法，当前字段事实通过 `AuditFieldFactsService.current_field_fact_pairs` 统一读取与配对。
- service 负责业务逻辑，不执行 SQL、不提交或回滚外层事务。跨实体查询使用对应 CRUD；唯一键冲突可用保存点隔离，不撤销整个请求。
- crud 是执行 SQL 的位置，只查询、写入和 flush，不提供 commit/rollback 代理。会话状态、保存点和文件联动直接使用 Session。
- domain 不导入 modules；integrations 只被 service 调用；graph 只调用 flow 函数。
- 不做包级重导出，调用方从具体模块导入。

数据访问示例：

```python
task = AuditTaskCRUD(db).by_no(task_no)
AuditTaskCRUD(db).flush()
```

## 事务与配置

- 普通接口由请求层的 `get_db` / `request_session` 在成功后提交、失败时回滚；业务 Service 和 CRUD 不提前提交。
- 后台任务由执行编排层管理明确工作单元：命令认领、远端调用前占位、进度、逐条结果、等待点和失败记录分别提交。`audit/execution/service/{commands,resume,flow}` 属于执行编排；材料、导入和通用后台线程编排位于对应实体的 `execution.py`、`preprocessing.py`。
- 后台线程只在请求提交成功后启动。目录删除先暂存，回滚前恢复、提交后清理；上传文件在回滚后核对真实引用再清理。CSV 继续通过 Session 事件与保存点参与回滚，不按提交位置另建机制。
- 场景、方案配置条目使用普通数据类，按数据类字段序列化到 `config_json`；不声明虚拟 SQL 表、外键或索引。`ConfigItem` 提供读取视图，不通过属性赋值修改配置。
- 配置修改通过 `services/shared/configuration.py` 的 `update_material/field/rule/section`，可修改字段由 `domain/config_changes.py` 声明；方法校验目标集合及字段名并统一标记 JSON 变更。名称、来源与引用的业务校验仍由所属 Service 负责。编译生成规则的派生身份、来源通过 `update_generated_rule` 同步；动态业务元数据通过 `update_extensions` 保留，不覆盖数据类固定字段。

## 执行内部契约

`domain/audit_state.py` 定义计划项、调度核对边界、规则结果、批次汇总与图/单规则状态。计划生成、主执行、批量抽取、结果保存与续跑共用这些结构；图节点和模型/工具步骤按原有方式返回局部更新，不新增持久化 checkpoint。渠道故障结构在 `domain/llm_failure.py` 定义，继续复用原故障分类。

冻结规则、模型消息、业务取值与证据内容仍按各自动态契约处理，不用内部调度类型限制业务字段，也不修改历史执行 JSON。

## 前端接口契约

`frontend/src/api/contracts/<业务>.ts` 统一声明服务端请求与响应类型，`api/<业务>.ts` 负责 HTTP 调用。任务详情、节点与字段直接使用 `AuditTask/AuditNode/AuditField`，不在 API 文件中追加平行的 View 类型；页面派生状态留在组件或 composable。材料上传与移除共用 `ReplacementImpact`，调用方从契约目录导入类型。

## 命名与注释

- 函数名说明动作和对象，类说明职责，避免“本实体服务”一类空泛描述。
- 同一份身份或缺项清单由一个函数生成，上下文和保存校验共同使用。
- 注释只解释业务约束、事务边界及反直觉原因，不重复代码、不记录修改过程。
- 简单函数用一句话说明；搬迁后删除空节标题、过期路径和连续空行。
- 错误明确上抛或交回既有模型修正流程，不吞异常、不伪造成功。

## 任务详情读取

`audit/task/service/detail.py` 组装任务当前视图，规则结果的名称和比较来源展示由 `rule_views.py` 负责。材料分类通过产物服务的 `material_classifications` 按上传 ID 批量查询，再读取实际已就绪产物；缺产物返回空缺，坏产物明确报错，不因读取优化改变质量限制或保存的数据。
