# 后端分层约定

本项目按 FastAPI 和 SQLAlchemy 的实际职责组织代码，不要求空的接口、实现类或额外包装层。

## 目录职责

| 目录 | 职责 |
| --- | --- |
| api | HTTP 路由、入参、依赖注入与响应组装 |
| services | 业务用例、执行编排、事务边界和视图组装 |
| repositories | 可复用的数据库查询与配置持久化 |
| entity | SQLAlchemy 实体，与 database/schema.sql 对齐 |
| schema/dto、schema/query、schema/vo | 写操作输入、查询条件、响应模型 |
| domain | 配置形状、引用编译、值转换及工具目录 |
| graphs | 固定任务图和单条规则执行器，不保存持久化 checkpoint |
| integrations | LLM 与文件处理、OCR、印章等外部服务适配 |
| operators | 模型可选择的本地工具实现 |
| middleware、common | 请求上下文、异常等公共能力 |

API 将业务操作交给服务层，不直接调用 repository。服务可以使用 repository 的公开接口或直接组织 ORM 操作；已有服务层查询不需要为分层再包一层。数据库实体不作为接口 response_model，Pydantic 模型不作为数据库实体。

## 三层内部按业务分目录

保留 `api`、`services`、`repositories` 三层，每层内部建立业务文件夹，再按职责拆分文件。以下路径均相对于 `backend/app`：

| 业务 | API 目录 | Service 目录 | Repository 目录 |
| --- | --- | --- | --- |
| 场景 | `api/scenario/` | `services/scenario/` | `repositories/scenario/` |
| 方案 | `api/plan/` | `services/plan/` | `repositories/plan/` |
| 审核任务与执行 | `api/audit/` | `services/audit/` | `repositories/audit/` |
| 材料与证据 | `api/material/` | `services/material/` | 暂无独立文件夹 |
| 报告与风险 | `api/report/` | `services/report/` | 暂无独立文件夹 |
| 规则库导入 | `api/imports/` | `services/imports/` | 暂无独立文件夹 |
| 系统状态与操作记录 | `api/system/` | `services/system/` | `repositories/system/` |
| 跨业务共用能力 | — | `services/shared/` | `repositories/shared/` |

文件跟随业务归属，不再往三层根目录堆放服务文件，也不建立混合多个业务的管理查询服务。只在存在实际持久化职责时增加 repository 文件；不为目录对称创建空模块。

各业务 API 包的 `__init__.py` 只汇总本业务路由，`main.py` 注册七个业务路由。目录名不作为 URL 的生成依据；人工对账接口已删除，材料处理只保留四项单项重试。服务与仓储包不重导出业务函数，调用方直接导入实际实现模块；没有旧路径兼容文件或惰性转发入口。

规则库和材料上传均为同步路由，由 FastAPI 放入工作线程；数据库 Session 在该线程创建、使用和关闭，文件写入及 Excel 解析不占用事件循环。

### 场景

`api/scenario/` 分为生命周期、配置查询、材料、字段、规则、报告章节与发布接口。

`services/scenario/` 中，`lifecycle.py` 维护场景主记录，`draft.py` 负责草稿初始化、锁定与配置提交；`materials.py`、`fields.py`、`rules.py`、`sections.py` 分别维护草稿配置。`publishing.py` 编译并保存发布快照，`versions.py` 在发布事务中分配版本号，`configuration.py` 组装配置视图，`query.py` 查询列表、选项与详情，`lookup.py` 提供存在性查询。

`repositories/scenario/` 按 `template.py`、`version.py`、`draft.py` 区分身份记录、发布版本和草稿配置。最新发布版本读取统一使用 `version.py`。

### 方案

`api/plan/` 分为生命周期、配置和创建任务接口。`services/plan/` 中，`lifecycle.py` 负责创建、复制、启停、删除与恢复，并明确拒绝任务反向生成方案；`configuration.py` 校验并保存定制，`compilation.py` 编译配置与同步系统规则，`views.py` 组装配置视图，`adjustments.py` 展示定制差异，`query.py` 处理列表与选项，`tasks.py` 编排从方案创建任务的命令。

`repositories/plan/plan.py` 查询方案主记录，`configuration.py` 读取方案的配置行。场景与方案的 JSON 配置持久化共用 `repositories/shared/configuration.py`。计算定义读取和引用改写仍位于 `domain/calculation_config.py`，方案计算启停解释位于 `domain/plan_calculations.py`。

### 导入、材料、报告与系统

`services/imports/` 按上传、查询、候选配置维护、转换、应用到草稿和生命周期拆分；`operations.py` 提交后台转换，`llm.py` 负责两轮模型转换，`workbook.py` 读取工作簿。

材料与证据管理查询分别位于 `services/material/documents.py`、`evidence.py`。报告查询、备注与归档、风险列表分别位于 `services/report/query.py`、`lifecycle.py`、`risks.py`。任务内的材料写操作与结果查询仍归审核业务。

`services/system/` 维护系统状态、后台操作和操作日志。文件存储、原始模型响应存储和共用命令处理位于 `services/shared/`，具体业务的后台提交入口留在对应业务目录。

管理列表共用 `common/pagination.py` 的分页结构，分页入参校验位于 `schema/query/`；筛选、计数、排序由对应业务查询服务负责。报告下载共用 `api/report/downloads.py` 的响应构造，各接口分别校验报告存在、正文可用和当前性。

## 审核模块

`api/audit/` 分为任务维护、执行命令、材料处理、结果查询与执行历史接口。

`services/audit/tasks/` 处理任务创建、复制、列表、详情、维护和材料上传。`creation.py` 负责实际业务写入，`copying.py` 编排幂等复制命令，`command_records.py` 保存命令记录，`documents.py` 处理上传、移除和输入变更失效，`processing.py` 组装材料处理状态。

`services/audit/` 按执行职责保留 `commands`、`rule_execution`、`rule_results`、`facts`、`views`、`state`、`evidence`、`artifacts`、`shared` 等模块。`material_retry.py` 提交 8018/8010/8003 的单项重试，`preprocessing.py` 运行材料流水线，`execution_history.py` 统一记录执行失效与原状态，`fact_context.py` 按完整字段身份投影事实。命令入口组织写操作，rule_execution 读取上游数据并保存产出，rule_results 保存规则结论、CSV 业务负载及证据关联，facts 处理事实索引及字段纠错，views 组装只读结果。rule_results 不提交事务，提交边界由 flow 中的实际执行步骤保持。

`services/audit/flow/` 按职责分文件：

| 文件 | 职责 |
| --- | --- |
| lifecycle.py | 任务与节点执行的建立、收尾、进度推进 |
| context.py | 材料前置处理、依赖计划、规则实例和模型上下文 |
| model.py | 单轮模型调用与既有循环上限的显式阻断 |
| tools.py | 真实工具调用与工具消息回填 |
| results.py | 候选结论校验和结果保存，保留已有人工结论 |
| errors.py | 单步及图运行失败的记录与错误暴露 |
| execution.py、shared.py | 当前执行身份核对、规则定位及 Agent 延迟加载 |
| runner.py | 将上述步骤绑定为图所需的 AuditNodeRunner 协议实现 |

`operations.py` 提交审核业务的后台命令，`executions.py` 查询跨任务的执行记录。工具适配与调用分别位于 `tools/handlers.py` 和 `tools/runtime.py`，模型风险判断位于 `risk_llm.py`。

规则结果状态集合和模型循环状态统一位于 domain/audit_vocab.py，`RULE_STATUS_LABELS` 与前端 constants/auditStatus.ts 使用同一组短标签（通过、异常、已完成产出、证据不足、已复核）。`COMPUTED` 表示“已完成产出”，具体抽取或报告语境仍按实际产物展示；它不等于审核通过。前端展示口径集中在 constants/auditStatus.ts，规则详情抽屉与列表通过 utils/auditRulePresentation.ts 复用纯展示逻辑。材料产物文案与颜色集中在 constants/materialProcessing.ts，任务执行状态使用 constants/labels.ts；同码按业务上下文表达，例如产物 READY 为“已就绪”、任务 READY 为“待执行”。

材料处理保留只读状态与四项单项重试：8018/8010/8003 通过 `/documents/{document_no}/artifacts/{artifact_type}/retry` 重试当前上传版本的该项产物，OCR 续查原 job_id，明确失败才新提交。结果未知的产物（PROCESSING / SUBMITTING）需用户显式确认后才重提，确认参数与每次调用历史随产物保存；整项审核仍不会自动重提未知作业。人工对账入口不再提供。

graphs/audit_graph.py 只组织任务固定生命周期，在 execute_rules 中串行遍历依赖计划；graphs/audit_rule_runner.py 负责单条规则的模型与工具循环，通过协议调用 services/audit/flow/ 中的真实步骤。commands.py 注入 runner.py 的实例；图模块不导入服务实现，也不在图回边中遍历规则或模型轮次。

业务取值的 CSV 读写统一经过 `services/audit/value_store.py`；数据库仍管理索引、状态、证据和报告。具体存储边界见[执行契约](规则库与审核执行契约.md)。

审核命令和视图分别从 `services/audit/commands.py`、`views.py` 导入。包初始化不加载命令实现；确需延迟加载的模型和后台执行依赖保留在实际调用点。

## 错误与请求追踪

错误响应使用 code、message、details、request_id，HTTP 状态码保留失败语义；成功响应不增加统一包装层。

- BusinessError 保留错误码、说明及业务详情，敏感键按 common/exceptions.py 的规则显式脱敏。
- 请求结构错误返回 422 / REQUEST_VALIDATION_FAILED；未知异常返回 500 / INTERNAL_ERROR，完整堆栈留在服务端。
- 请求上下文和 CORS 为响应提供 X-Request-ID；流式响应开始后的异常仍由服务端暴露，不替换成成功响应。
- 前端保留错误码、HTTP 状态和请求编号，区分通信失败、超时、主动取消及非法响应。超时或取消不能推断后台操作成败，后台状态由操作查询接口报告。

事务由对应写服务负责，异常处理不伪造成功。缺少真实输入、外部调用失败或模型输出无法保存时，应保留可定位的错误，不以空值或假结果代替。
