# 后端分层约定

本项目借鉴 SSM 的分层思路，但按 FastAPI 和 SQLAlchemy 的实际特点组织，不复制 Java 的接口与实现类模式。

## 依赖方向

```text
api -> service -> repository -> entities/database
 |        |
 |        +-> domain / integration
 +-> dto / query / vo
```

- `api/`：只处理 HTTP 路由、入参、依赖注入和响应组装，不写 ORM 查询和事务。
- `services/`：业务用例、流程编排和事务边界。Python 模块本身就是实现，不强制创建空洞的 `service/impl` 配对。
- `repositories/`：封装 SQLAlchemy 查询和持久化细节，不组装 HTTP 响应。
- `entities/`：按业务域拆分的 SQLAlchemy 数据库实体，字段必须与 `database/schema.sql` 一致。
- `dto/`：写操作和应用服务的输入对象。
- `query/`：列表筛选、分页等查询条件及校验。
- `vo/`：只读的 HTTP 响应视图对象。
- `domain/`：不依赖 HTTP 的业务规则、值对象与编译/计算逻辑。
- `integrations/`：外部服务的适配器。
- `middleware/`：请求上下文、身份与权限等横切能力。
- `common/`：真正跨业务模块的小型基础对象；不作为无归属代码的堆放处。

## 边界规则

1. API 不得直接调用 `db.scalar/scalars/execute/commit/rollback`。
2. 一个写操作涉及幂等、恢复或多表写入时，事务必须在 service 层完整结束。
3. Repository 返回实体或持久化投影；业务文案、权限判断和响应格式属于 service/VO。
4. Pydantic 模型不与 SQLAlchemy 实体混用。数据库实体不作为 API `response_model`。
5. 公共异常统一由 `common/exceptions.py` 映射，API 不捕获异常后伪造成功响应。

## 当前结构

SQLAlchemy 实体按导入、场景、场景草稿、方案、任务、报告、操作、检索和 Agent 业务域放在 `entities/`。Pydantic 请求与响应模型按业务域放在 `dto/`、`vo/`。分页校验位于 `query/`，请求上下文位于 `middleware/`，统一响应基类和全局异常处理位于 `common/`。
