# 任务业务取值文件

业务文件采用 UTF-8 BOM、中文列名。日常查看先看 `values.csv` 和 `rule_results.csv`，不需要解析模型返回 JSON。当前格式版本为 5，每个任务固定维护 `tasks/{task_no}/value_batches/current/` 下的四张表，路径登记在 `audit_task.value_file_json.batches[0].files`。每次写入按 `(记录类型, 记录ID)` 合并并逐个原子替换四张表，不会再新增 UUID 批次目录。

| 文件 | 每行含义 | 主要业务列 |
| --- | --- | --- |
| values.csv | 一版字段候选、字段有效事实或计算结果 | 业务类别、业务编号、名称、材料名称、期间、报表口径、主体范围、声明类型、取值说明、原文、候选值、有效值、单位、币种、修订号、写入时状态、取值来源、原文依据 |
| rule_results.csv | 一次保存的规则结论 | 业务编号、名称、材料名称、规则类型、审核要求、计算公式、结论状态、结论原因、风险等级、风险处置、处理建议、原文依据、展示协议版本、各类明细数量 |
| rule_items.csv | 一条判断依据、一项实际产出或一个缺失事项 | 业务编号、名称、材料名称、明细序号、明细类别、核查项/产出编号/缺失事项、实际取值、依据说明、原文、字段名称、产出材料名称、产出值、字段状态、产出单位、产出币种 |
| value_details.csv | 结构化值的一个属性或数组节点 | 业务编号、名称、材料名称、业务项目、属性名、数组序号、值类型、值；所属项目及节点关系用于还原结构 |

记录类型、记录ID、写入批次等技术关联列放在表格右侧；按名称、材料、业务编号筛选即可查看。字段候选是抽取原文及待确认取值，字段事实是实际执行输入，两者用途不同；无效候选可以保留候选值，但有效值为空。规则结论不再重复保存整份 verdict，字段事实也不再重复保存模型 judgement。新产出的 extracted_values 展示从产出明细组装，不重复保存。

`rule_items.csv` 用“明细类别”区分三类明细：判断依据（basis）、实际产出（outputs）、缺失事项（missing_items）。早先按类别拆成三张表，现在合并成一张，同名不同义的列按各自标签分别保留，例如“实际取值”属于依据、“产出值”属于产出。

## 单元格和值类型

可读业务值与类型各自一列，例如“有效值”和“有效值类型”。支持 text、integer、float、decimal、boolean、date、datetime、null、object、array。金额和十进制不经过 float，布尔值写 true/false，日期采用 ISO 格式。导入 Excel 时将业务值列、ID 和编号列设为文本，避免自动转日期、科学计数或截断精度；CSV 引号本身不能阻止 Excel 自动改写类型。

类型列为空表示没有保存该属性；null 表示明确空值，值单元格留空；text 配空白单元格表示空字符串。零值和 false 都是实际值。object/array 的值列留空，在 value_details.csv 按同一记录、写入批次和所属项目维护子节点，不能往该单元格贴 JSON。空对象、空数组保留根节点。缺失类型、非法值、缺明细、重复节点和数组序号不连续会明确报错，不填默认值。

原文依据是唯一允许放在单个 JSON 单元格里的复杂值：它有固定业务形状，展开成明细行只增加行数。其它 object/array 仍按上面的严格树编码写进 value_details.csv。

多条依据、产出、缺项在 `rule_items.csv` 各占一行，明细序号从 0 开始。主表的数量必须与实际明细相符。补充业务属性（如工具核查明细、计算定义、风险来源、历史报告正文）逐属性展开到 value_details.csv，不丢失嵌套值和类型。历史转换保留的不同旧结论在“历史结论差异”项目展开，不伪装成当前结论。

## 维护和生效

- 同一记录按 `(记录类型, 记录ID)` 定位；更新时替换该记录在四张表中的主行和明细，其他记录原样保留。每个任务只登记一个 `current` 文件集，不按业务编号合并不同记录。
- 业务名称、口径、写入时状态、要求等描述列用于查看和定位，来自任务冻结配置或写入时数据库索引；编辑这些描述不会修改规则配置、数据库状态或当前版本。
- 调整业务规则应修改场景/方案配置；正式纠正字段应使用页面字段纠错入口，它会建立新修订并失效相关输入。直接编辑 CSV 仅适合停机数据修复，不会自动建立修订、同步数据库结论状态、重算下游或更新已生成报告。
- 程序写入固定文件集时会先写临时文件并逐个原子替换。读取四表与写入共用跨进程任务锁；任务详情、风险和报告先持锁再读数据库清单与取值。写入持锁至外层事务结束，保存点成功不会提前释放。模型上下文的只读取值仅在加载文件时持锁，不把文件锁延长至模型调用。停机数据修复时先备份四张表和数据库，保留关联列、记录数量及文件清单；直接修改 CSV 不会同步数据库结论状态。
- 四表全部写入、关闭并同步文件后才更新清单；清单与业务索引由同一数据库事务提交。每层保存点与外层事务分别记录改写前快照，失败只恢复对应层级；保存点成功保留外层快照，外层回滚仍能恢复。会话未提交就关闭时同样恢复。快照位于原文件旁边，以完整目标路径区分任务，不依赖系统 TEMP 所在盘。
- 提交之后仅清理临时快照；若临时文件被占用，单独记录 ERROR 日志及剩余路径，不把已提交业务伪报为失败。`.locks/task-values/` 是固定锁文件，`.rollback`/`.restoring` 是恢复文件，清理工具保留这些文件；应结合失败日志人工核对恢复文件，不能当作业务 CSV 删除。
- 数据库与文件系统仍不具备跨介质的崩溃原子性：进程被强制终止、断电、磁盘故障不等同于可捕获异常的事务回滚；本实现不承诺自动恢复此类故障。文件丢失或内容损坏继续明确报错。
- 固定 `current` 文件集的清单变化会整体重读，避免更新同一数量记录时沿用会话缓存中的旧内容。

## 旧格式

格式版本不是 5 的任务在读取时明确报 `TASK_VALUE_FORMAT_UPGRADE_REQUIRED`，不会静默降级或混读。当前工作区没有随代码提供的转换脚本；旧格式任务需要按目标格式单独准备数据。

每条规则在产出、证据核对完成后只写一次四表；已有批次读取一次后复用表格完成校验和合并。但固定文件仍需全量重写，长任务的累计 I/O 成本尚未通过运行测量，不宣称已解决全部性能问题。
