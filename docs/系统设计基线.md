# baoli-v4 系统设计基线

更新：2026-09-20。性质：历史架构基线；部分条款待重审（legacy only）。

> 2026-09-16 评审提示：用户已要求以 LLM 降低配置负担、保留 09 关系表，并由审核 Agent 根据 State 按需调用工具。本文“固定工具计划、工具选择仅导入期、规则引擎作为唯一判断主体、单文件材料位、自动配对不在范围、逐项人工确认”等口径属于历史基线，正在重新设计。最新需求及待评审方案见 [场景化审核Agent需求与设计评审稿.md](场景化审核Agent需求与设计评审稿.md)。下文保留用于对照历史设计，不表示新方案已获准编码，也不能用旧条款否定用户的新要求。

本文记录历史设计的边界和不变量。当前实现差距、外部未知和真实验收状态只记在 [当前状态与问题台账.md](当前状态与问题台账.md)。本文不是运行成功证明，也不是新方案的批准基线。

## 1. 目标与范围

baoli-v4 是合同审核验证版：业务人员维护审核配置，系统把配置发布为不可变版本，用真实业务材料执行审核，保存事实、证据、人工结论、风险和报告。

主链路：

```text
维护规则库或页面配置
-> 确定性校验，保存即生效为当前场景配置
-> 发布绑定该场景配置的方案版本
-> 创建并冻结审核任务
-> 上传真实材料
-> 文件处理、字段抽取、规则检查
-> 人工复核
-> 风险评定和报告
```

系统保持 FastAPI、Vue 3、MySQL、LangGraph 和本地文件存储。当前范围不扩展为多租户平台、通用流程设计器、任意公式引擎、微服务体系、消息队列、Redis 或独立向量数据库。多份同类材料自动配对、跨文件汇总和通用合同问答属于待业务与能力确认的范围，不能由本历史基线默认支持或禁止。

样本只用于发现结构和验证行为，不是业务权威。样本里的阈值、等级、币种、单位、材料映射和处理动作，未经用户确认不得写成默认业务规则。

## 2. 核心对象

| 对象 | 含义 | 版本规则 |
| --- | --- | --- |
| 审核场景 | 某类审核的完整材料、字段、规则、风险和报告定义 | 配置可编辑、保存即生效；方案发布与任务创建时各冻结一份快照 |
| 审核方案 | 对当前场景配置选择可复用的审核范围 | 发布形成不可变方案版本，不跟随场景配置变化 |
| 审核任务 | 使用一个方案版本审核一组真实材料 | 创建时冻结执行快照，后续发布不改旧任务 |
| 材料位 | 任务要求的业务材料角色 | 业务名称与外部识别类型必须分开保存 |
| 字段定义 | 从某材料取得的业务事实定义 | 场景内以稳定 key 标识 |
| 规则定义 | 对材料或字段执行的检查 | 编译为固定工具、输入、参数和证据要求 |
| 任务事实 | 某次任务从真实材料取得的值 | 绑定上传版本和执行版本，不覆盖历史 |
| 证据 | 支撑事实或判断的原始依据 | 绑定任务、材料、文件版本和产物版本 |
| 人工结论 | 工作人员对事实或规则结果的决定 | 独立于系统原判断，绑定具体待办版本 |

关系是：场景配置 -> 方案版本 -> 审核任务（方案发布时冻结当时的场景配置）。一个材料可以定义多个字段；一条规则可以引用多个字段；一个字段也可以被多条规则使用。

`material_name` 是给业务人员看的材料位名称，例如“主合同”；`material_type` 是外部材料识别服务接受的类型标识。两者语义不同，不能复制、猜测或硬编码映射。详细规则见 [规则库与审核执行契约.md](规则库与审核执行契约.md)。

## 3. 标识、引用和版本

后端为材料、字段和规则生成场景内稳定 key。key 不由 LLM 生成，不使用中文名称、文件名或 Excel 行号代替。Excel 中的业务编号保存为 `source_ref`，用于追溯，不作为跨场景全局主键。

字段引用必须按明确作用域解析：

- 材料名称在同一场景配置内唯一；
- 字段由“所属材料 + 字段名称”唯一确定；
- 风险和报告使用明确编号或唯一名称；
- 未知、重复或不唯一引用明确失败，不使用向量相似度或 LLM 猜关系。

场景配置每次保存都会编译出完整的 `manifest_json` 与哈希，并保存为当前生效版本。方案版本固定引用它发布时刻的那个版本。任务创建时保存 `task_schema_json`，至少冻结材料范围、字段范围、规则、工具策略版本、允许能力范围、参数约束和报告范围。新场景、新方案或新规则不得无声改变历史任务；工具调用的实际步骤由新方案 State 记录。

历史节点版假设每个材料位当前只使用一份文件；这不是新场景内核的通用约束。真实规则库未声明材料数量时，新方案必须由场景配置材料实例和配对策略。无论单份还是多份，补传、替换和移除都产生新的任务输入修订；旧文件、旧事实、旧规则结果和旧报告保留为历史，但不得继续充当当前依据。

## 4. 配置生命周期

页面编辑、Excel 导入和复制都进入同一份场景配置。配置保存即生效，保存时经过确定性编译校验：

```text
来源 -> 场景配置 -> 引用与能力校验 -> 生效（方案与任务据此冻结快照）
```

配置不完整时（例如只有材料还没有规则）保存仍然成功，但配置未生效：
页面必须显示具体原因与缺失项，已发布版本保持为上一个可用版本。

规则库导入的预检查必须绑定来源、目标场景、草稿修订和配置哈希。任何会改变发布结果的修改都使旧预检查失效。生效与发布不得自动补业务值、删除问题、停用规则或复用另一目标的确认结果。

节点版规则库的表头、枚举、引用和算式由程序确定性解析。LLM 可以在兼容旧格式或自然语言规则导入时提出工具和字段映射建议，但建议必须有来源、通过结构校验并由用户确认。配置发布后业务范围和版本不能被模型临时改写；规则 Agent 的运行期工具步骤属于新方案的 State/工具契约，不由本历史段落预先禁止。

## 5. 执行图与职责

导入图负责读取、提议、确认和编译；审核图负责按任务快照推进。审核节点顺序为：

```text
MATERIAL_CHECK
-> DOCUMENT_PREPARE
-> FIELD_EXTRACTION
-> INTERNAL_VALIDATE
-> CROSS_VALIDATE
-> MANUAL_REVIEW（存在待办时）
-> RISK_RATING
-> REPORT_OUTPUT
```

**分层与依赖方向（2026-09-20 起）**：

```text
API 路由
-> 应用用例 / 命令入口（services.audit.commands、各 admin/query 服务）
-> 领域规则（domain/*：manifest、node_rulebook、capabilities、file_quality、audit_vocab…）
-> 通过明确接口调用持久化（models）与外部集成（integrations/*）
```

- `domain` 不依赖 `services` / `api` / `graphs` / `integrations`；
- 图编排（`graphs/*`）只负责状态推进、interrupt、resume 与节点调度，不承载业务规则：
  审核节点实现由调用方在调用时经 `AuditGraphContext["nodes"]` 注入（`services.audit.flow`），
  因此 `graphs` 与 `services` 之间没有模块级依赖，也不存在循环；
- 审核执行内部按职责分层：`commands → flow → reviews → {reporting, views, quality, rules}
  → facts → state → evidence → artifacts → shared`，只允许向下依赖；
- 外部服务的供应商细节只出现在 `integrations/*`，业务层读的是归一化后的内部结构。

历史实现把 LangGraph 限定为编排、checkpoint、interrupt 和 resume，并由规则引擎负责具体判断。新方案改为：LangGraph 还承载规则/抽取子图 State，LLM 负责业务语义判断，确定性工具提供可核对事实，Agent 在已发布范围内按 State 调用工具；文件服务负责上传与产物，人工复核处理仍无法确定或有冲突的内容。

节点没有配置时必须显示“未配置/跳过”，不能写成通过。业务不合格是一次成功执行得到的异常结果；外部服务失败、配置错误或证据不可用是技术失败或无法判断，不能混为业务通过。

`REPORT_OUTPUT` 是固定系统节点：即使场景没有额外业务报告章节，也要生成可追溯的系统事实报告，并标明业务章节未配置。零业务章节不等于零报告，也不等于审核范围完整。

## 6. 统一工具注册表

文件格式、文件大小、重复文件、字段比较、数值计算、LLM 校验、风险汇总和报告渲染都是执行能力。每项能力必须在一个统一注册表中有唯一 `tool_id`，并至少声明：

| 元数据 | 用途 |
| --- | --- |
| `tool_id` 与业务标签 | 稳定引用和界面显示 |
| 支持节点 | 限制能力可出现的位置 |
| 输入与参数 schema | 编译期校验类型、数量、必填和单位 |
| 所需产物与证据 | 执行前准备真实依赖 |
| handler | 唯一运行入口 |
| 输出状态与失败语义 | 统一规则结果和错误表达 |
| 版本 | 保证旧场景和旧任务仍可按原语义执行 |

注册表是后端能力的单一事实来源。profile 的允许值、manifest 编译校验、运行时分发和前端选项必须从注册表派生或与其做启动/发布前一致性校验，不能各自维护互不校验的名单。缺 handler、节点不兼容或 schema 不完整时，应在导入或发布阶段明确阻断，不能等任务运行时才报未知能力。

历史实现口径是“Agent 只在导入期提出工具计划，运行期严格照冻结顺序执行”。新方案不采用这条作为通用限制：运行期规则 Agent 可以在任务范围、工具策略版本和事实快照约束内按 State 选择下一步工具，但每次调用、结果和依据都必须持久化，业务范围与能力版本仍然冻结以保证可审计。

确定性问题优先由确定性工具处理，例如真实字节数、声明格式、内容哈希、Decimal 比较和日期比较。语义判断才使用 LLM；印章主体相似检索只返回候选，不替代人工结论。

## 7. 事实、证据和人工复核

原始抽取事实不可被重跑或人工编辑覆盖。每次抽取都要关联任务、字段、材料、上传 ID、执行批次、原始值、规范值、状态和证据。系统另存“当前事实选择”，新事实生效时旧事实退出当前选择但仍可追溯。

人工结论至少保存：目标事实或规则结果、系统原判断快照、修改前后值、决定、理由、依据类型、待办版本和提交命令。人工值可以基于明确人工说明生效，但必须标为人工依据；不能拿旧文件引文证明新值。

字段事实先复核，依赖规则随后重算，再展示新的规则待办。`PRESENT` 错值和 `NOT_PRESENT` 漏值都应能纠正。新上传、新抽取或待办集合变化后，旧草稿和旧人工结论不得自动套用。

证据至少按任务、材料位、上传版本、产物类型、产物内容哈希和对象身份隔离。有页码或坐标时只有在页映射、坐标系和尺寸真实可核对后才高亮；否则只展示真实文本或文件入口，不伪造定位。

## 8. 命令、幂等与恢复

所有会改变导入作业或审核任务的操作必须先锁定对象，再检查当前状态、活跃命令和输入修订。幂等键相同且规范化输入相同，返回原命令结果；同键不同输入明确冲突。

业务事务与 LangGraph checkpoint 是两套提交，必须通过持久命令和业务结果对账。恢复遵循事实：

- 命令未执行：核对输入修订后认领原命令；
- 外部服务已有作业号：继续查询原作业，不重新提交文件；
- 请求可能送达但结果未知：记录未知，只有真实幂等或查询契约支持时才能自动对账；
- 业务结果已提交但图未推进：复用原结果推进图，不重复业务写入；
- 正在等待 interrupt：只有匹配当前待办版本的持久命令才能 resume；
- checkpoint 暂时不可读：本次操作失败，不能把任务永久标记失败；
- checkpoint 确认缺失或损坏：返回具体诊断，不能新建空图伪装恢复。

任何外部调用都不得用静默重试、空结果、模拟响应或替代服务制造成功。

## 9. 结果和错误语义

规则结果至少区分：合格、不合格、无法判断、不适用、未执行、待复核。节点状态至少区分：待执行、执行中、成功、失败、阻断、跳过。读取失败不等于空数据，证据不足不等于业务正常，未配置风险也不等于无风险。

错误应包含稳定错误码、中文消息、业务对象定位和 request ID。可安全返回时，规则库错误还应包含 Sheet、行、列、单元格和原值。供应商密钥、签名地址、磁盘绝对路径和原始敏感响应不得直接展示。

报告必须来自同一份当前有效事实、规则结果、人工结论和输入修订快照。分别表达“文件已生成”“审核范围完整”“风险可以判断”；三者不能用一个“成功”代替。未实现的格式不显示为可下载，更不能改扩展名冒充真实文件。

## 10. 完成标准

代码存在、配置已填写和真实链路已验证是不同结论。只有使用用户提供的真实规则库和真实业务材料完成下列链路，才能说验证版跑通：

1. 导入并完整读取真实规则库；
2. 处理全部来源行、引用、待确认和停用项；
3. 保存场景配置并发布方案版本；
4. 创建任务并上传与材料位匹配的真实文件；
5. 执行文件处理、字段抽取、内部校验和交叉校验；
6. 完成人工复核并重算依赖；
7. 生成风险和报告；
8. 刷新或中断后能按原任务恢复，历史仍可追溯。

不得用生成文件、空白文件、假响应或其他材料类型的真实文件替代缺失样本。缺少真实材料时，应明确停在缺少什么，而不是绕过该节点。
