# 规则库与审核执行契约

## Excel 解析与配置

Excel 的 Sheet 名、数量和布局不决定业务执行流程。全部非空工作表交给 LLM，不要求固定模板、表头或工作表绑定；是否完整理解业务内容仍取决于实际模型返回。

导入正常包含两轮模型请求：

1. 第一轮读取 Excel 内容，建立 materials、fields、rules、calculations、report_sections 五类业务目录；每项只含内部引用、原名称、编号、状态和来源行，不重复生成完整执行配置。
2. 第二轮接收第一轮目录 JSON、同一 Excel 的完整原文和最终格式说明，生成完整执行配置；对照原文修正漏项或误写，整理跨表引用、同名字段及计算依赖，不接收程序业务诊断。

两轮推理强度可通过 BAOLI_RULEBOOK_LLM_REASONING_EFFORT 配置，原样作为 reasoning_effort 发给供应商，仅影响规则库解析。当前本地 deepseek-flash 使用 low（保留推理）；留空不传该参数，采用供应商默认。供应商不支持所配置参数时明确报错，不自动降级。DeepSeek 默认 high 的说明见[官方推理模式文档](https://api-docs.deepseek.com/guides/thinking_mode)；深度推理耗时与正文生成耗时都计入现有请求总时限，不以扩大超时或截断内容代替完整解析。

第二轮结果保存在 import_job.proposals_json。导入记录保留源文件路径、文件身份和作业状态。业务对象的 origin 保存真实 Sheet 名、主来源行、补充来源行及这些行的原始单元格；模型只返回位置，程序从工作簿附上原始行，不让模型抄写来源原文。来源不存在时明确报错。完整工作表清单和布局快照不重复存库，需要时重新读取源文件。两轮原始响应分别保存到 data/llm_responses 下，background_operation.raw_response_path 指向最近保存的返回。第二轮失败时明确报错，不采用第一轮结果代替。

程序在模型返回边界读取必要数据结构，不预审公式或业务合理性，也不逐项筛除业务定义。模型补充属性保存在 business_context；字段 instruction 描述实际抽取动作，类型、单位、币种、期间和报表范围使用各自属性，不把未填写项拼成长段抽取要求。

candidate_ref 用于导入对象之间的引用，写入草稿时映射为内部键；计算的 FIELD 参数也映射为内部字段键，避免同一原编号在不同材料或期间展开后互相覆盖。rule_key 是当前规则身份；普通规则 rule_code、材料/字段 source_id、报告 report_code 保留原始业务编号，没有编号留空。计算 source_id 保存原编号，rule_code/result_code 为执行引用，无原编号时使用明确的内部引用。普通规则的 rule_role 区分 CHECK 与 RISK。字段、普通规则、计算结果和报告之间的引用按原文整理，缺失对象不虚构，停用项不因被引用而自动启用。

统一的是对象结构和引用方式，不统一或改写业务名称、表头、编号、判断标准与报告章节。业务对象的名称保留原字词及限定语；同名不同材料、期间和口径分别保存。字典、说明与历史变更日志用于理解当前定义，不生成额外执行规则。origin 随导入、草稿、发布和方案配置传递；字段派生抽取项继承原字段的来源编号，报告执行项继承原报告编号，内部执行编号单独保留。

解析结果页按材料、字段、审核规则、计算规则和报告章节展示紧凑的 Element Plus 表格，支持搜索、状态筛选与单项编辑。规则类型、适用材料、输入字段和依赖规则分别展示；字段类型、单位、币种及计算参数来源也使用独立列。长内容通过省略提示及编辑抽屉查看完整原文，不改写业务要求。修改通过 PATCH /import-jobs/{job_no}/proposals/{group}/{candidate_ref} 保存到 proposals_json，修订号随保存递增；写入草稿使用修改后的结果。未编辑属性和引用保持原值，待确认与暂停状态分别保留。已写入的导入结果只供查看，后续修改在场景草稿进行。

场景草稿和方案业务定义保存在 config_json；发布版本保存编译后的配置，任务创建时冻结方案配置及生效范围。保存草稿不做发布预审，实际发布时编译。字段定义派生抽取项，计算定义派生计算项，报告章节组织报告项；系统目前仍保留这套编译机制。

发布成功后删除场景草稿；创建发布快照与删除草稿同一次提交，发布失败保留草稿。GET /scenarios/{scenario_code}/configuration 默认读取当前配置：有草稿时读取草稿，否则读取已发布版本；接口仍可通过 view=DRAFT 或 PUBLISHED 明确选择来源，配置页不提供来源切换。列表数量与编辑页采用同一来源，并标明是否有未发布修改。GET /scenarios/{scenario_code}/draft 只读已有草稿，不隐式创建。编辑保存或确认导入时才创建草稿；导入请求的 expected_scene_revision 为 null 表示确认时没有草稿。

配置状态统一为 CLEAR（启用）、PENDING（待确认、暂不执行）、DISABLED（暂停、不执行）；计算使用 status，其余定义使用 config_status。待确认定义完整保留，可导入、保存及发布，不阻止其他已启用规则执行；字段不抽取、计算不运行、报告章节不生成。管理员明确启用后转为 CLEAR，仅修改名称或要求不自动确认。LLM 只按原文状态填写，不因缺少参数或口径自行设为待确认；生效规则依赖待确认项时，保留具体缺项说明，不自动执行依赖项。

## 规则执行与工具

执行契约版本为 rule_library_v1。RULE_EXECUTION 是关联执行批次和结果的技术容器，不是用户可编排的业务阶段。

审核上传仅接收 PDF、PNG、JPEG、TIFF；规则库 Excel 的导入不受影响。审核图在建立执行批次后、加载规则计划前运行 prepare_materials，按材料流水线推进：MATERIAL_CLASSIFY（8018 原件校验）完成后并行进入 DOCUMENT_PARSE（8010 去章）和 SEAL（8003 原件印章）；去章完成立即进入 OCR（PaddleOCR 读取去章产物），不等待印章分支。每次前置执行中，8018、8010、8003 各有独立的顺序队列，上一份材料离站后该服务继续下一份，不等整份材料全部处理完。OCR 作业各自提交、独立续查。各步骤使用独立数据库会话，调度线程统一保存执行进度；只有全部已上传材料四项均成功，才进入业务规则。某一步失败仅跳过该材料依赖该步的后续处理，其余分支和材料继续保存真实结果；全部已调度步骤收尾后汇总错误、阻断审核。已完成产物复用，OCR 续查已有作业，不自动重提。8018 类型是否匹配作为真实结果保留给规则判断，不按置信度或不匹配结论自行添加业务阻断。

前置步骤与产物编号记录在本批次 result_json.preprocessing；每份材料的 stages 分别保存四项的等待、排队、运行、成功、失败或依赖失败跳过状态，errors 保存真实错误。成功收尾仍保留该记录。材料处理状态支持查询四项服务，8003 结果未知时使用与 8018/8010 相同的显式对账入口。未上传材料留给业务规则说明缺失，不生成处理成功记录。

生效项依次进入同一循环：读取规则与真实输入 → 调用模型 → 按需执行工具并回填 → 核对实际产出结构 → 保存结果 → 下一条规则。显式字段、规则和计算结果引用决定顺序，报告排在其他生效项之后。缺少、停用、未选中或循环依赖会带具体说明进入对应规则上下文，不阻止无关项。

任务图固定为八个节点：load_task → execute_current_node → prepare_materials → load_evaluation → execute_rules → finalize_node_execution → advance_workflow → save_node_result。建立批次失败时直接返回错误，前置失败时终止；正常路径没有图回边，图步数不随规则数量或模型轮次增长，也不扩大 LangGraph 默认步数限制。

load_evaluation 从本次任务冻结配置生成一次依赖计划，计划保留实际规则定义。execute_rules 按计划串行调用 graphs/audit_rule_runner.py；每条规则创建独立状态，在程序循环中调用现有模型、工具和结果校验入口，保存提交后再加载下一条的实际输入。单条模型或工具错误按现有语义明确记录，存储及程序异常向任务调用方传播。空计划直接汇总结束，普通规则、抽取、计算和报告使用同一执行器，不按场景分支。

LLM 直接完成抽取、计算与判断。可用工具从当前真实目录取得，不保存逐工具、逐规则授权矩阵；已有比较、计算、材料存在性、文件质量等本地工具仍可由模型选择，没有判定实现的独立质量工具不提供给模型。

| 工具 | 作用 |
| --- | --- |
| TASK_DATA_READ | 默认读取 OCR 正文 Markdown；也可明确读取 SEAL 印章或 MATERIAL_CLASSIFY 校验产物 |
| RULE_LIBRARY_QUERY | 查询本任务冻结的生效规则，不读取后来修改的草稿 |

DOCUMENT_PROCESS 已不向模型提供，前置程序直接调用真实服务。没有输入字段事实且需要抽取字段的执行项，首轮仅提供 TASK_DATA_READ，并要求原生工具调用；取回材料后恢复本条可用工具并允许形成最终结论。普通字段从去章 OCR Markdown 抽取，artifact_source=SEAL 的字段从原文件印章产物抽取；印章主体与正文主体分别取值后按原规则比较。工具请求和返回在本次运行内存中流转，专门的工具调用账本及前端记录面板已删除；原始模型诊断仍可能包含工具请求，见问题台账。

带工具请求使用原生 tool_calls，无工具请求使用 JSON 对象响应模式。结论格式、引用身份或声明产出错误回填同一条规则，由模型继续修正。既有 llm_tool_max_rounds 默认为 12，设为 0 关闭该轮次限制；不以默认结果代替失败。

轮次按单条规则的实际模型调用计数，处理下一条时从零开始；工具执行和程序步骤不额外占用轮次。每条结果摘要记录 loop_count，批次 loop_count 为各条实际轮次之和。轮次耗尽保存 LLM_TOOL_LOOP_LIMIT，继续处理其他规则，批次最终明确显示未完成；设为 0 时也不会受到任务图默认 25 步的间接截断。

审核图无 checkpointer，一次调用执行当前容器内的规则。切换规则时重置本条消息和工具结果；不提供持久化图状态恢复。audit_task.checkpoint_json 只是任务进度信息。

## CSV 与数据库

每个任务按业务列保存取值：values.csv 保存字段候选、有效事实和计算结果，rule_results.csv 保存规则结论；依据、产出、缺项分别保存在 rule_basis.csv、rule_outputs.csv、rule_missing_items.csv，结构化属性逐节点展开到 value_details.csv，不把整个返回 JSON 放入单元格。名称、材料、口径、单位、原因和建议可直接按列查看。格式版本 3 的 value_file_json.batches 按生效顺序登记不可变六表批次；全部文件落盘后才更新引用，引用与业务索引由同一数据库事务提交。相同记录 ID 取最后一个生效批次的主记录及其明细；事务和保存点回滚不覆盖旧值，仅留下未引用文件。读取按会话和生效清单增量缓存，清单回退时重新加载。旧三列文件和版本 2 共享业务表需显式转换，维护方式见[任务取值 CSV 维护说明](任务取值CSV维护说明.md)。

| 数据 | 当前存储位置 |
| --- | --- |
| 导入最终配置、场景草稿、方案、发布及任务配置 | 数据库 JSON |
| 字段原文值、规范值 | CSV 的 TaskFieldValue 记录 |
| 字段事实、计算结果、单位、币种及判断 | CSV 的 TaskFact 记录 |
| 规则 outputs、业务结论及相关上下文 | CSV 的 RuleResult 记录 |
| 字段、事实、规则结果的身份、版本、当前位和状态 | 数据库索引记录 |
| 规则结论文本、风险等级、执行诊断及输入摘要 | 数据库 rule_result |
| 引用证据原文、所属文件或产物关系 | 数据库 evidence |
| 报告正文、状态及范围说明 | 数据库 audit_report |

Decimal 和日期通过编码保留精度与类型，结构化值以 JSON 保存。数据库已删除字段值与事实值的专用取值列，但诊断仍包含模型完整响应和输入取值，因此目前不能称为“业务值完全不落库”。

CSV 缺文件或已有索引对应的记录缺失时明确报错；审核、事实投影、任务详情及风险展示统一严格读取，区分未产生记录与记录丢失。文件系统与数据库没有分布式事务；不可变批次隔离未提交的取值，不能替代提交后文件的持久保管。

## 结果、证据与报告

用户结果区展示状态和直接业务原因。模型 message 使用短语或简短句子，不复述执行步骤、工具名称、内部编号或审核标准；具体取值与依据放 basis，最终缺项放 missing_items，处理建议放 next_action。确认材料未载明与无法读取必须区分，执行完成不等于审核通过。

已有旧格式结果不重算、不改写业务状态：页面根据保存的状态、抽取值和明确 NOT_PRESENT 状态显示简短摘要，不能从长说明的关键词猜原因；完整原说明保留在默认折叠的技术详情中。旧记录只有通过状态时显示“符合要求”，具体判断原因仍以原说明为准。此次展示修改仅静态核对，未运行测试、构建或模型。

模型结果状态为 PASSED、ABNORMAL、COMPUTED、NOT_APPLICABLE、EVIDENCE_INSUFFICIENT。抽取和计算必须返回声明身份的真实 outputs；程序核对结构、身份及可存储类型，不重新裁定业务结论。结构化字段使用 Draft 2020-12 JSON Schema，当前 STRUCTURED 接口接收 JSON 对象。

字段保存候选与有效事实的索引，计算保存派生事实索引，取值写入 CSV。已有人工确认值不由模型覆盖。证据引用核对实际工具、事实或本条上下文中的上游 rule_result_id；证据保存原文和文件、产物关系，不要求页码或坐标。OCR 内部位置数据用于正文处理。

TASK_DATA_READ 引用保留实际读取结果的 artifact_id、material_key 和可选 quote_text；提供原文时需在读取文本中找到。字段引用给出 output_code（本规则声明的字段键），绑定本次抽取版本并传递到规则结果；上游事实和规则引用传递已有证据。仅引用工具产物而未提供引文时，只记录来源，内容核对为 NOT_CHECKABLE，不自动拼接全文或生成原文。引文核对与业务结论相互独立。

OCR 轮询首次立即查询；本地截止时间到期明确报超时，不等同于供应商失败，也不自动重提。真实供应商状态与 extractProgress 按变化保存，状态查询返回最近记录的页数及更新时间；界面不估算页数或百分比。

失败重跑只失效模型产生的字段候选和事实，保留人工确认值及人工纠错版本；已确认的人工值仍作为后续计算和校验输入。模型返回与人工确认值不同的值时明确报告冲突，不覆盖人工值。

人工审核暂不启用，新模型结果不返回 PENDING_REVIEW，也不创建人工待办或等待点；尚未确认的业务要求以 EVIDENCE_INSUFFICIENT 说明。历史未确认状态及字段纠错记录保留。

报告章节可引用字段、计算结果和普通规则结论。执行时关联当前事实及本批次结果，缺少数据须在相关章节说明，不编造内容。正文与文件格式要求分别记录：目前保存、下载支持 Markdown、纯文本和 HTML，未生成格式明确标记。

有无法执行或缺失结果的项时，批次及任务可标记 BLOCKED，保留结果并允许重新执行。COMPLETED 只表示执行结束，不表示全部检查通过。

唯一下载入口是报告下载。数据库结构直接维护在 backend/database/schema.sql，应用不自动迁移；当前问题与验证边界见[问题台账](当前状态与问题台账.md)。
